# Discord 포럼 정산의 Prisma 실행 방식

[구현 명세와 ERD](정산기능-spec.md)의 업무 테이블은 Prisma Client 모델로 접근한다. SQL은 Prisma가 생성하고, 애플리케이션은 값을 모델 쿼리에 전달한다. 관계·제약·삭제 큐 트리거는 PostgreSQL 마이그레이션에 정의한다.

## 커넥션과 트랜잭션

- 다모아와 같은 방식으로 봇 프로세스에서 `pg.Pool` 한 개를 만들고 `PrismaPg` 어댑터를 통해 Prisma와 공유한다. 풀이 연결의 재사용과 반환을 맡고, 프로세스 종료 시 Prisma와 풀을 닫는다.
- 정산·계좌를 쓰거나 조회 결과와 응답 의존성을 함께 저장할 때는 콜백형 `$transaction`을 사용한다. 콜백 안에서는 전달받은 `tx`로만 호출한다. Discord 승인, 결과 발행, 답장 삭제 HTTP 호출은 트랜잭션 밖에서 처리한다.
- 업무 트랜잭션은 `Serializable`이다. 한 쪽이 계좌·정산을 읽고 응답을 등록하는 사이 다른 쪽이 데이터를 수정하면서 응답 등록을 놓치는 경우를 막는다. Prisma의 쓰기 충돌·교착 오류 `P2034`는 제한적으로 재시도한다. 수정·취소는 포스트·작성자·버전·취소 여부를 조건에 넣어 갱신한다.
- 포스트·계좌 advisory lock이나 선행 `SELECT FOR UPDATE`는 사용하지 않는다. 같은 행을 실제로 바꿀 때 PostgreSQL이 거는 잠금은 따로 제어하지 않는다.

## 명령별 모델 작업 순서

| 명령 | 순서 |
| --- | --- |
| `/정산` 제출 | 포스트 `createMany(skipDuplicates)` → 기록 `createMany(skipDuplicates)` → 배분 `createMany` → 답장 및 정산 의존성 `create`. 같은 Discord 제출 ID 재처리 시 기존 기록을 읽는다. |
| `/정산확인` | `SettlementShare.findMany`로 현재 포스트의 내 부담액과 결제자 조회 → TypeScript에서 `bigint`로 상대별 합산 → 수신자 계좌를 `findMany` 한 번으로 조회 → 답장과 계좌·정산 의존성 `create`. 계좌가 없는 수신자도 의존성에는 넣는다. |
| `/정산세부` | 현재 포스트에서 내 부담액 행이 있는 유효 기록 `count` → `findFirst(skip)`로 최신순의 한 건과 표시 허용된 부담액 조회 → 답장 및 해당 정산 의존성 `create`. |
| `/정산세부` 이전·다음 버튼 | 기존 답장의 소유자·포스트·만료 여부 확인 → 같은 상세 조회 → 기존 답장에 연결된 기록 갱신 → 활성 상태를 다시 확인하고 Discord에서 같은 메시지 수정. 원래 삭제 예약을 유지한다. |
| 정산 수정 | 현재 기록과 참여자 `findFirst` → 작성자·버전 조건의 `updateMany` → 기존 배분 `deleteMany` → 새 배분 `createMany` → 이전 답장 `updateMany` → 새 답장 등록. |
| 정산 취소 | 작성자·버전 조건의 `updateMany`로 취소 시각 저장 → 기존 참여자 조회 → 이전 답장 `updateMany` → 새 답장 등록. |
| `/계좌등록` | 이전 계좌 `findUnique` → 값이 다르면 `upsert` → 수신자의 계좌가 반영된 답장을 `updateMany` → 완료 답장 등록. |
| `/계좌삭제` | `deleteMany` → 삭제한 행이 있으면 수신자의 답장을 `updateMany` → 완료 답장 등록. |

결과 전송 직전에 응답이 아직 활성 상태인지를 조회한다. 같은 사람이 같은 포스트와 명령 종류의 조회를 다시 열면 새 결과를 보낸 뒤 그보다 오래된 활성 응답을 무효화한다. 정산 기록이 아직 없는 Discord 포스트는 응답의 `scopePostId`로 구분한다.

모델 호출 수는 PostgreSQL에 실제로 전송되는 SQL 문 수와 다를 수 있다. 통합 테스트에서 Prisma 7.10.1이 전송한 업무 SQL은 참여자가 한 명인 `/정산` 7문, 수신자가 한 명인 `/정산확인` 9문, 한 건을 연 `/정산세부` 8문이었다. 트랜잭션 제어문·Graphile 내부 쿼리를 제외했고, 답장 발행 전 상태 조회와 해당 경로의 이전 답장 정리를 포함했다. 이 횟수는 테스트 데이터의 관측값이다. 테스트는 바인딩 값 없이 SQL 텍스트만 받아 횟수를 출력하고 명시적 잠금 SQL이 없는지 확인한다.

## 삭제 작업과 커밋

[마이그레이션](../prisma/migrations/20261119000000_forum_settlement/migration.sql)의 트리거는 비공개 답장이 생성될 때 애플리케이션이 저장한 생성 시각 + 1분에 실행할 작업을 등록한다. 상태가 `active`에서 `invalidated`가 되면 같은 작업 키로 즉시 실행 작업을 등록한다. PostgreSQL이 이 트리거를 실행하므로 업무 변경이 롤백되면 작업도 함께 롤백된다.

워커는 Graphile에서 받은 응답 ID로 암호화된 토큰을 읽고 Discord 원본을 삭제한다. 완료·만료 후 토큰을 비우고, 데이터베이스를 장시간 점유하는 외부 요청을 만들지 않는다. Graphile의 작업 조회·폴링은 Graphile 내부 쿼리다.
